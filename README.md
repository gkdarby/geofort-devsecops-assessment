# GeoFort DevSecOps Assessment

This repository demonstrates a secure DevSecOps delivery workflow using:

- Java and Maven
- Jenkins CI/CD
- Docker
- Trivy vulnerability scanning
- Checkov IaC scanning
- Terraform
- Syft SBOM generation
- Cosign image signing and verification
- Kubernetes
- Kyverno admission control

The project includes application source code, CI/CD configuration, Kubernetes manifests, security policies, infrastructure-as-code examples, and security evidence.

---

## Overview

The purpose of this assessment is to demonstrate how security can be integrated throughout the software delivery lifecycle instead of being performed only at the end of deployment.

The workflow builds and validates a Java application, scans the application and container image, analyzes infrastructure-as-code, generates a software bill of materials, signs the resulting container image, verifies the signature, and applies Kubernetes admission controls.

The implementation is intended to be lightweight and repeatable. It is not presented as a complete production platform. Where controls are currently operating in reporting or audit mode, the intended production enforcement approach is documented.

## CI/CD Security Workflow

The Jenkins pipeline performs the following major activities:

1. Fetch application source code from GitHub.
2. Validate the Java, Maven, Docker, Trivy, AWS CLI, and Cosign build environment.
3. Validate and compile the Java application.
4. Run unit tests.
5. Run PMD static code analysis.
6. Run Checkstyle analysis.
7. Generate JaCoCo code coverage results.
8. Run Trivy filesystem scanning for vulnerabilities, secrets, and misconfigurations.
9. Package the Java application as a WAR file.
10. Run SonarQube analysis.
11. Enforce the SonarQube Quality Gate.
12. Publish the application artifact to Nexus.
13. Scan the Dockerfile using Trivy.
14. Run Checkov against Terraform infrastructure-as-code.
15. Build the Docker image.
16. Scan the Docker image using Trivy.
17. Generate a CycloneDX SBOM using Syft.
18. Start and test the application container.
19. Perform an OWASP ZAP baseline scan.
20. Push the tested image to Amazon ECR.
21. Push the image to Docker Hub.
22. Sign the exact Amazon ECR image digest using Cosign.
23. Verify the Cosign signature.
24. Scan Kubernetes manifests using Trivy.

This workflow introduces security checks throughout the software delivery lifecycle rather than relying on a single security review before deployment.

## Security Gate Decisions

Not every security scanner currently operates as a hard pipeline gate.

The assessment intentionally demonstrates both reporting controls and blocking controls.

Current behavior:

```text
Trivy filesystem scan       -> Reporting
Trivy container scan        -> Reporting
Checkov IaC scan            -> Reporting
Kyverno non-root            -> Audit
SonarQube Quality Gate      -> Blocking
SBOM generation             -> Blocking
Cosign signing              -> Blocking
Cosign verification         -> Blocking
Approved registry policy    -> Enforce
```

The intent is to demonstrate how findings can first be observed and evaluated before controls are moved into full enforcement.

---

## SonarQube Quality Gate

SonarQube analyzes the Java application for code quality and security issues.

The SonarQube Quality Gate is a hard pipeline control.

If the Quality Gate does not return:

```text
OK
```

the Jenkins pipeline stops.

This prevents application code that does not meet the defined quality or security threshold from progressing further through the release process.

---

## Trivy Filesystem Scanning

Trivy scans the application workspace for:

```text
Vulnerabilities
Secrets
Misconfigurations
```

The pipeline uses:

```bash
trivy fs \
  --scanners vuln,secret,misconfig \
  --severity HIGH,CRITICAL \
  --exit-code 0 \
  .
```

The current implementation records and archives findings without automatically stopping the pipeline.

This allows the assessment to demonstrate security evidence collection and review.

In a production implementation, selected findings could be converted into blocking release controls.

---

## Trivy Container Image Scanning

After the Docker image is built, Trivy scans the image for HIGH and CRITICAL vulnerabilities.

The current assessment uses:

```bash
--exit-code 0
```

This allows findings to be collected without automatically stopping the pipeline.

A production security gate could instead use:

```bash
trivy image \
  --severity HIGH,CRITICAL \
  --exit-code 1 \
  IMAGE
```

This would cause Jenkins to fail when qualifying vulnerabilities are found.

A reasonable production policy would normally block:

- Critical vulnerabilities
- High vulnerabilities with a known fix
- Vulnerabilities known to be actively exploited
- Findings that violate organizational security policy

Exceptions should require documented and time-limited risk acceptance.

- security approver

## Infrastructure-as-Code Security Scanning

Checkov is used to analyze Terraform infrastructure before changes are deployed.

The assessment includes representative Terraform security group configuration.

Example command:

```bash
checkov -f terraform/sg.tf
```

The scan produced both passed and failed checks.

One clear security finding was:

```text
CKV_AWS_382
Security group allows unrestricted egress to 0.0.0.0/0
```

Unrestricted outbound access allows a workload to communicate with any destination permitted by the network path.

The recommended remediation is to apply least privilege by restricting outbound access to only the required:

```text
Destination CIDRs
Security groups
Ports
Protocols
```

The specific requirement should be based on the actual dependencies of the application.

---

## Checkov Scan Context

Some Checkov findings were generated while scanning an individual Terraform file instead of the entire Terraform project.

Terraform resources may reference resources defined in other files.

Because of this, some checks may not have complete cross-file context during an isolated file scan.

Scanner results should therefore be validated before remediation.

The intent is not to ignore findings, but to confirm whether each finding represents an actual security weakness in the complete infrastructure configuration.

---

## Checkov Pipeline Integration

The Jenkinsfile contains a Checkov IaC scanning stage.

The stage checks whether a Terraform directory exists in the Jenkins application workspace.

If Terraform is present, Checkov runs against the directory.

If Terraform is not present in that application workspace, the stage records that the Terraform security evidence is maintained separately.

The current assessment pipeline uses:

```text
--soft-fail
```

This allows Checkov findings to be collected without stopping the lab pipeline.

In a production implementation, the preferred approach would be either:

- a dedicated CI/CD pipeline for the infrastructure repository, or
- a controlled checkout of the infrastructure repository during the pipeline

High-risk Checkov findings could then become blocking deployment controls.

## SBOM Generation

Syft is used to generate a Software Bill of Materials for the built container image.

Example:

```bash
syft geofort/geofort-global-dynamic:latest \
  -o cyclonedx-json=sbom.json
```

The SBOM is generated in CycloneDX JSON format.

It records the software packages and dependencies found inside the container image.

This provides visibility into exactly what software was included in a release.

---

## Why the SBOM Matters

A container image may pass its security scan today and become vulnerable later when a new CVE is published.

The SBOM allows the organization to determine whether a newly disclosed vulnerability affects previously released images.

Example workflow:

```text
New CVE published
        ↓
Search retained SBOMs
        ↓
Identify affected images
        ↓
Determine risk and exploitability
        ↓
Update affected dependency
        ↓
Rebuild image
        ↓
Rescan
        ↓
Generate new SBOM
        ↓
Sign new image
        ↓
Redeploy
```

This makes the SBOM useful for continuous monitoring and incident response, not just the original software release.

---

## SBOM Pipeline Gate

SBOM generation is treated as a required pipeline activity.

If Syft is missing or cannot generate the SBOM, the Jenkins stage fails.

This prevents the pipeline from silently releasing an image without the expected software inventory.

The SBOM is archived as pipeline evidence.

## Container Image Integrity with Cosign

Cosign is used to digitally sign the container image after it is pushed to Amazon ECR.

The pipeline does not sign only a mutable image tag such as:

```text
latest
```

Instead, Jenkins retrieves the immutable ECR image digest.

Example:

```text
588738572310.dkr.ecr.us-east-1.amazonaws.com/geofort-repo@sha256:<digest>
```

Cosign signs this exact digest.

This creates a cryptographic relationship between the signature and one specific container image.

If the image contents change, the digest changes.

The previous signature would therefore not represent the modified image.

---

## Cosign Key Management

The Cosign private key is stored in Jenkins Credentials.

It is not committed into GitHub.

During the Jenkins signing stage, the private key is temporarily reconstructed inside the build workspace.

The temporary private key file is permission-restricted.

After the image is signed, the temporary file is deleted.

The Cosign public key is also obtained through Jenkins credentials for verification.

After verification completes, the temporary public key file is removed.

This reduces the risk of private key material being stored permanently in the source repository or build workspace.

---

## Cosign Verification

After the ECR image digest is signed, Jenkins immediately verifies the signature using the trusted Cosign public key.

Representative command:

```bash
cosign verify \
  --key cosign.pub \
  repository@sha256:digest
```

If the signature cannot be verified, the pipeline fails.

This helps ensure that the image being promoted is the image that was signed by the trusted CI/CD process.

## Kubernetes Security with Kyverno

Kyverno is deployed inside Kubernetes as an admission control layer.

It evaluates Kubernetes resources submitted through the Kubernetes API server.

The assessment demonstrates three controls:

```text
Non-root workload validation
Approved container registry enforcement
Cosign image signature verification
```

Kyverno provides an additional security layer after CI/CD because it can validate what is actually being submitted to the Kubernetes cluster.

---

## Non-Root Container Policy

The `require-nonroot` Kyverno ClusterPolicy checks whether Pods in the `geofort-app` namespace define:

```yaml
securityContext:
  runAsNonRoot: true
```

The policy currently operates in:

```text
Audit
```

mode.

The existing application does not currently satisfy the desired non-root security requirement.

Kyverno PolicyReports identified failures against the application Deployment, ReplicaSets, and Pods.

The application is still allowed to run because the policy is being introduced safely in Audit mode.

---

## Kyverno Audit to Enforce Strategy

A new Kubernetes security rule should not always be immediately enabled in Enforce mode against existing applications.

Doing so can unexpectedly block production workloads.

The preferred rollout process is:

```text
Create policy
      ↓
Audit
      ↓
Identify violations
      ↓
Remediate application
      ↓
Test application
      ↓
Confirm compliance
      ↓
Move policy to Enforce
```

The `require-nonroot` policy demonstrates this rollout approach.

Once the GeoFort image has been updated and tested to run successfully as a non-root user, the policy can be changed from Audit to Enforce.

---

## Approved Container Registry Policy

The `require-approved-registry` Kyverno policy operates in:

```text
Enforce
```

mode.

Pods in the `geofort-app` namespace are required to use images from the approved Amazon ECR repository:

```text
588738572310.dkr.ecr.us-east-1.amazonaws.com/geofort-repo
```

If a workload attempts to use an image from an unapproved registry, Kyverno denies the Kubernetes admission request.

This reduces the possibility of deploying:

- untrusted images
- arbitrary public images
- images that bypass the approved CI/CD process
- potentially malicious container images

---

## Image Signature Admission Control

The assessment also includes a Kyverno image verification policy for GeoFort Amazon ECR images.

The policy works with Cosign image signatures.

The goal is to ensure that a Kubernetes workload does not rely only on the fact that an image exists in ECR.

The image must also have the expected trusted signature.

The overall flow is:

```text
Developer commits code
        ↓
Jenkins builds application
        ↓
Security scans run
        ↓
Docker image is created
        ↓
Trivy scans image
        ↓
Syft creates SBOM
        ↓
Image is pushed to ECR
        ↓
Jenkins retrieves immutable digest
        ↓
Cosign signs digest
        ↓
Cosign verifies signature
        ↓
Kubernetes deployment requested
        ↓
Kyverno evaluates admission policies
        ↓
Approved workload is admitted
```

This provides software supply-chain traceability from source code to Kubernetes deployment.

## Evidence Retention

In a production environment, security evidence should be retained automatically in a centralized and access-controlled evidence repository.

Evidence should be immutable where practical.

Retention should follow organizational and compliance requirements.

This evidence can support:

- security assessments
- RMF activities
- continuous monitoring
- audit reviews
- incident investigations
- release approvals
- vulnerability management

This approach reduces the need to manually recreate security evidence during every assessment.

## Security Tool Failure Handling

Security controls can fail because of operational problems, not only because a vulnerability was found.

Examples include:

- scanner vulnerability database download failure
- scanner service outage
- disk exhaustion
- dependency repository outage
- missing security tooling
- network connectivity failure
- container registry authentication failure

A scanner failure should not be treated as a successful security scan.

For release-critical security controls, the preferred behavior is:

```text
Fail Closed
```

If the required security validation cannot be completed, the pipeline should stop rather than release an unvalidated artifact.

---

## Emergency Release Handling

There may be rare situations where an urgent business requirement requires a deployment even though a security gate cannot be fully satisfied.

This should not result in permanently disabling the security control.

A temporary exception should require explicit authorization.

The exception should document:

- business justification
- affected security control
- vulnerability or finding
- known security risk
- application owner
- security approver
- compensating controls
- remediation owner
- remediation deadline
- exception expiration date
- follow-up review date

Once the exception expires, the control should return to normal enforcement unless the exception is formally renewed.

---

## False Positive Handling

Security scanners can generate findings that may not be exploitable in the specific environment.

A finding should be validated before it is permanently suppressed.

A false-positive exception should document:

- scanner finding ID
- affected component
- technical justification
- supporting evidence
- approving authority
- compensating controls if required
- expiration date
- review date

This prevents organizations from accumulating undocumented permanent exclusions.

---

## Newly Discovered Vulnerabilities

An image that was considered acceptable when it was originally released can become vulnerable later.

This happens when new CVEs are disclosed after deployment.

Previously approved container images should therefore be rescanned periodically or continuously.

The response process can be:

```text
New vulnerability disclosed
        ↓
Identify affected SBOMs
        ↓
Identify affected images
        ↓
Determine severity and exploitability
        ↓
Update dependency or base image
        ↓
Build new container
        ↓
Run security scans
        ↓
Generate new SBOM
        ↓
Sign new digest
        ↓
Verify signature
        ↓
Deploy remediated image
        ↓
Retire vulnerable image
```

This is an important part of continuous monitoring.

## Secrets Scanning

Trivy filesystem scanning is configured with:

```text
--scanners vuln,secret,misconfig
```

This provides basic detection of potential secrets stored inside source code or configuration.

Examples include:

- API keys
- passwords
- tokens
- cloud credentials
- private keys

Secrets should not be hard-coded into Git repositories.

Production secrets should instead be managed through an approved credential or secrets management platform.

---

## Credential Handling

The Jenkins pipeline uses Jenkins Credentials for sensitive values rather than hard-coding them in the Jenkinsfile.

Examples include:

- GitHub credentials
- Nexus credentials
- Docker Hub credentials
- Cosign private key
- Cosign password
- Cosign public key

Temporary credential files created during pipeline execution are deleted after use.

Cloud access should ideally rely on short-lived workload identities or IAM roles instead of long-lived static access keys.

---

## Air-Gapped and Restricted Environment Considerations

A DevSecOps workflow may need to operate in an environment without direct Internet access.

Security tooling can still function if required dependencies are mirrored internally.

Examples include:

- internal Trivy vulnerability databases
- internal container registries
- internal Maven repositories
- internally hosted scanner binaries
- internal artifact repositories
- internal copies of SBOM tools
- offline Cosign verification
- trusted vulnerability database update packages

Updates should be transferred into the restricted environment through an approved process.

This allows security automation to continue in disconnected or highly controlled environments.

## Assumptions and Tradeoffs

This assessment demonstrates security automation and engineering decisions without attempting to create a complete production platform.

Some controls intentionally operate in reporting or Audit mode so findings can be evaluated without immediately breaking the existing workload.

Current control posture:

```text
Trivy image scanning      -> Reporting
Trivy filesystem scanning -> Reporting
Checkov                   -> Reporting
Kyverno non-root          -> Audit
SonarQube                 -> Blocking
SBOM generation           -> Blocking
Cosign signing            -> Blocking
Cosign verification       -> Blocking
Approved registry         -> Enforce
```

A production environment would determine blocking thresholds according to:

- vulnerability severity
- exploitability
- availability of a remediation
- workload criticality
- organizational risk tolerance
- compliance requirements

The objective is not to blindly block every scanner finding.

The objective is to create repeatable security controls with clear decisions, evidence, accountability, and traceability.
